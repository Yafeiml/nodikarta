---
name: nodicarta-sync
description: Use Nodicarta (脉络) when the user confirms a project change worth handing off, even if they only ask for two sentences for a stand-up or handoff. Examples include “就用第二稿，帮我写两句晨会用”, “先试一轮再决定”, and “把验收结论记到脉络”. Skip wording-only edits to supplied material, hypothetical examples, and local-only work.
---

When the work changes, ask what a collaborator on another device would otherwise have to redo, might use incorrectly, or might promise too soon. Save the relevant change while the reason and evidence are available. An explicit request to remember is optional. At handoff or close, check once for a change still missing. Skip casual ideas, routine activity, and repeated readings that add no evidence. Use the project's working language.

Honor “只读”, “只在本机”, “不要记” and equivalent limits even if write tools are visible. An ordinary recall or public-wording question needs no write. If the directory or client lacks write access, provide the handoff in the conversation and identify the missing permission when relevant. Do not use a different client or queue the content to get around that limit.

If the user's message confirms a change in this project and also asks for a short stand-up or handoff summary, make the project check before replying and keep the reply brief. If they are only polishing or summarizing supplied material, or working through a hypothetical example, skip the sync workflow. Before writing, confirm the bound project with `list_projects`, search the same subject and target via `search_project_knowledge(query)`, and open each plausible match with `get_knowledge_history(itemId)`. Compare the latest full body, evidence and pinned versions. If they already cover the handoff, give the brief reply without a new revision. If the finding or evidence changed, update the matching item at its latest version and retain its other valid findings. Create a new item only for a distinct subject or scope, or when the search finds no matching entry. Both the device and the client need write access.

For work in progress, use a searchable title and ordinary prose in the existing knowledge entry. Say what was chosen and why, how far approval extends, what remains open, and the agreed next action. Include an owner, due date or approval source only if supplied. Cite the instruction or artifact that establishes the choice without copying the conversation. A working draft may be selected for revision while distribution is pending. An agreed experiment authorizes that experiment; the broader product or delivery commitment remains open.

Revise the handoff when progress changes, including completion or abandonment. Keep that history searchable. Record a subsequent adoption with its own scope and evidence if it has a different lifetime. For a new pending handoff, omit optional `validity`. The body carries its working status. Keep existing classified decisions and measurements intact.

Write the current conclusion so it makes sense on another machine. For an installation or test, name the observed device or environment and when you checked it (including the time zone). For a local check, read the machine name so a later reader can identify “this computer”. A submitter can report on another device. Separate observations from assumptions and from decisions. Prefer paths relative to the workspace or user home.

When the source establishes how a claim applies, include `validity` in the commit:

- Use `{"kind":"fact"}` for an event that already happened, such as which input a delivered design used. Keep its original evidence and pinned versions.
- For an adopted rule, use `kind="decision"` with its explicit `scope`. A new publication or suggestion alone does not establish adoption. If an independent decision explicitly replaces another in the same scope, read the predecessor's latest revision and provide its `supersedesItemId` and `supersedesVersion` in the new decision's validity. To correct the existing entry itself, use the usual top-level `itemId` and `baseVersion`.
- For measurements, reuse the original item for the same device and the same measured property. Use `kind="observation"`, the actual `subject` (device or environment), and `observedAt` copied from the measurement, including the UTC offset. Cite the measurement in `evidence`. For any change to an existing observation's title, body, evidence or asset references, explicitly include its `validity`. When correcting the record for the same measurement, keep its original observation time. An offline query, a file's publish date or a reread of old notes supplies no new measurement.

Keep distinct claims separate when their scope or lifetime differs. A source with no reliable classification can remain unclassified. There is no expiry date to enter.

If an open Codex chat cannot see newly configured MCP tools yet, run the bundled `scripts/call-knowledge.cjs` from the chat's working directory, using the script path relative to this skill. Pass the tool name as the only argument and its JSON parameters on standard input. It asks Codex about the project bound to that directory without starting a model turn. If the directory is unbound, its ownership is ambiguous, or access was revoked, report the status Edge returns. Keep the submission in its original project.

Call `submit_knowledge_commit` with a fresh UUID as `requestId`, a specific `title`, a `body`, and `evidence`. For a revision, read `get_knowledge_history(itemId)` and pass the existing **itemId and its latest version as baseVersion in the tool arguments**. Omitting the ID creates a separate entry even if the text cites the old ID. The new body and evidence replace those fields in the current view, so carry forward still-valid findings and their sources. Date the change so the old observation remains intelligible. For a new entry start at `baseVersion=0`. Include `relatedTaskId` when the entry has a known task. Omit secrets, personal information, and full conversations.

If a decision refers to published project assets, pin their actual IDs and versions in the optional `assetRefs` array. Each reference takes `role`, `assetId`, and `version`, plus an optional `locator` such as "page 3, top right". Use `deliverable` for the output the decision applies to, `used` for the original actually used, and `evidence` for the supporting material. Each decision accepts up to 32 references and at most one deliverable. For example, if poster v3 uses logo v1, reference poster v3 as the deliverable and logo v1 as used, then explain the choice in the body. Check the version with `get_asset(assetId, version)` when needed. A selected working draft can be the pinned output; state its review stage in the body. If its original is local, use an authorized relative reference in `evidence` and say where it can be reached. Use `publish_asset` only when the user has requested sharing that original in the project and the connection permits it.

Omitting `assetRefs` on update retains the preceding revision's references. To change them, check the history and submit the complete replacement array. Pass `[]` only to remove all references intentionally. Use `get_asset_decisions(assetId, version)` to read the decision back from its deliverable.

After a timeout, retry with identical content and the same `requestId`. If Edge returns `queuedLocally`, report the request ID as pending sync. Report the entry and version as saved after Core acknowledges them. On version conflict, read the latest history and preserve the evidence from both sides. Submit any reconciled change with a new request ID and the latest base version.
